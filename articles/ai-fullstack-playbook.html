AI 全端開發

從規格到程式：AI 端到端協作開發 4 項全端功能的 Playbook 實驗

這次實驗想回答一個問題：如果讓 AI 先寫規格書，再依照自己寫的規格完成前後端與資料庫開發，效率與品質能到什麼程度？

實驗設計

Phase II 需要在短時間內交付 4 項功能，涵蓋前端、後端、資料庫結構與排程通知：

  • 進度甘特圖：計畫與實際雙列顯示、工作天演算法、假日色塊、逾期判定與自動排程。
  • 假日月曆管理：新增、修改、刪除，Excel 批量匯入匯出，並與甘特圖的工作天計算整合。
  • 逾期自動提醒：每日排程檢查，逾期第 3 天與第 7 天發送通知，並依層級通知主管。
  • 通知紀錄查詢：瀏覽發送紀錄、統計卡片，以及成功／失敗篩選。

依據 Phase I 相同複雜度的經驗，傳統（不使用 AI）開發估計需要 10 個工作天。

實驗假設

讓 GitHub Copilot 先產出規格書，再依照自己產出的規格完成開發（AI 程式碼佔比 ≥ 90%），並以自動化整合測試取代傳統人工 code review，可以進一步縮短有效開發工時。

執行流程

  1. 確認業務需求，並準備專案慣例文件 copilot-instructions.md（多語系、元件規範、資料庫命名規範）。
  2. 由 Copilot 依需求與慣例產出規格書 spec.md 草稿。
  3. 人工審核規格一次，確認欄位對照、狀態流程與 API 規格；有偏差就回饋給 Copilot 修正。
  4. 每個功能模組各發一個提示，由 Copilot 端到端產出後端、前端與資料庫結構。
  5. 以 35 個以上的 API 整合測試自動驗收；測試失敗時，把失敗現象回饋給 Copilot 修正。
  6. IT 測試通過後交付 UAT，並彙整效益數據。

開發效率：各功能工時對照

同一時期只有 80% 時間投入這個系統，因此「有效工時」以實際紀錄工時 × 80% 計算。

即使是含工作天演算法與色塊邏輯、最複雜的甘特圖，有效工時仍縮短一半。關鍵在於規格書裡有詳細的欄位對照表與演算法數字範例。

品質：用自動化測試把關

  • 35 個以上的 API 整合測試全數通過，IT 測試完成。
  • 甘特圖的邊界條件（跨週末、跨假日、逾期首日、緩衝判定）另以人工驗證。
  • 逾期通知採冪等設計：同一任務、同一天數只發送一次，不會重複通知。

撰文時 UAT 仍在進行中；提示詞輪數、AI 程式碼實際佔比與規格缺陷率等數據，將於 UAT 完成後補上。

學到的事

有效的做法

  • 規格書中的欄位對照表與演算法數字範例，是 AI 產出品質的關鍵。
  • 把系統慣例寫成文件（copilot-instructions），能明顯減少不符規範的程式碼。

需要改進的地方

  • 甘特圖「逾期首日」的色塊邏輯，AI 第一版有邊界錯誤，需要人工修正。複雜的視覺邏輯需要更詳細的規格描述。
  • 下次會為複雜演算法提供更多邊界案例，並嘗試 100% 時間投入，取得更純粹的加速數據。

什麼情況適合這樣做

適合不適合
有詳細規格書可作為 AI 的上下文（欄位對照 + 演算法範例效果最好）規格只有文字描述，缺乏欄位對照與邊界範例

風險與緩解

風險緩解方式
AI 產出的規格本身有邏輯偏差至少一次完整人工審核；缺陷率超過 10% 就回到 AI 二輪修正
規格與實際業務需求不一致審核時邀請業務方參與，並以測試案例驅動規格驗證
AI 程式碼缺少防禦性檢查整合測試必須涵蓋邊界條件，未通過不得交付
為了追求 90% AI 比例而犧牲效率90% 是目標不是紅線，工時改善優先於 AI 佔比
自動化測試無法涵蓋的業務邏輯保留 UAT 作為最後一道防線
