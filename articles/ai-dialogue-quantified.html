AI 協作量化

AI 對話可量化：以 chat.json 驗證系統維運優化成果

AI 協作的效益常被說成「感覺快很多」。這次我把 GitHub Copilot 的對話匯出檔 chat.json 當成資料來源，實際量化一次 HBase/Phoenix 整合任務花了多少提問、多少 Token，又省下多少時間。

背景：一次看似簡單的資料源整合

系統需要從 HBase/Phoenix 讀取量測資料，提供分析與報表使用。直接引入 phoenix-core、沿用既有的資料庫連線方式後，很快遇到啟動錯誤、套件版本衝突，以及上線後可能不穩定的風險。

這類問題通常要花 3–5 個工作天反覆排查。這次我全程和 GitHub Copilot 協作，並把對話紀錄保存下來，事後用它來量化 AI 協作的成本與效益。

根因：為 OLTP 設計的連線池，不適合 OLAP 查詢

既有系統使用 HikariCP 管理 Oracle 連線。它的設計前提是「短連線、快查詢、立刻歸還」，適合大量短交易的 OLTP 場景。Phoenix/HBase 屬於 OLAP 場景：查詢頻率不高，但單次查詢可能要跑數十秒，而且會跨多台 RegionServer 掃描資料。

一個簡單的比喻

HikariCP 像高速公路收費站：窗口固定，每輛車很快通過。Phoenix 像長途客運站：每班車要開很久，座位又固定，後面的人只能一直等。

如果直接套用 Oracle 的連線池設定，可能出現以下狀況：

  • 連線被長查詢佔滿，新的查詢等待 30 秒後逾時，使用者感覺系統「間歇性卡住」。
  • 長時間閒置的連線被防火牆切斷，但連線池不知道連線已失效，接著出現錯誤。
  • 加大連線數也沒有用，因為問題是連線被長時間佔用，最後只能靠重啟恢復。

解法：輕量連線池與借用／歸還模式

  1. 輕量連線池：預設最多保留 10 條連線，遇到尖峰時可按需建立，不必強制排隊等待。
  2. 背景健康檢查：發現失效連線就立即丟棄並重建，避免拿到「已死」的連線。
  3. 借用／歸還模式：讓開發者明確掌握連線的生命週期，長查詢也能安全歸還。
  4. 開發環境自動初始化：在 Windows 開發機啟動時，自動處理 Hadoop 需要的 winutils，減少新成員的環境設定步驟。
PooledConnection conn = connManager.borrowConnection();
try {
    // 執行耗時查詢（5–50 秒都可以）
    queryFromPhoenix(conn.getConnection());
} finally {
    connManager.returnConnection(conn);   // 確保歸還
}

用 chat.json 量化 AI 協作

chat.json 中每一次提問都帶有 metadata：promptTokens（輸入 Token）、outputTokens（輸出 Token），以及 editedFileEvents（新增、修改、刪除了哪些檔案）。把這些欄位整理出來，就能看見 AI 協作的真實成本。

為什麼 294 個字的提問，會變成 25,922 個輸入 Token？

常見的誤解是「輸入 Token 就是我打的字」。實際上，AI 回答前會把所有上下文一起讀進去：

AI 實際讀入的內容估計 Token
使用者輸入的 294 個字約 300–500
系統提示詞（內建指令）約 5,000–8,000
以 #file: 引用的程式碼檔案約 10,000–15,000
先前的對話歷史約 3,000–5,000
其他模型設定資訊約 2,000–3,000
實測合計25,922

Token 花在哪裡

  • 一次到位的提問：輸入約 15,000、輸出約 1,500 Token，效率最高。
  • 需要多輪修正的提問：一個例外處理問題來回修正 3 輪，前兩輪的輸出（761 + 2,157 Token）沒有產出可用程式碼，浪費比例達 75.1%。
  • 概念釐清型的提問：輪數多、輸出量大，但屬於學習成本，不是效率問題。

結論：總 Token 中約 15–20% 花在多輪修正。如果每個提問都使用「引用檔案 + 明確產出 + 約束條件」的高效模板，預估可再減少 15–20% 的總消耗。

風險與緩解

風險緩解措施

套件版本不匹配鎖定 Phoenix/HBase 版本，使用公司提供的套件
測試覆蓋不足設定最小覆蓋率門檻（> 80%）

給下一次 AI 協作的建議

  • 先引用相關檔案，再描述問題，讓 AI 一開始就有完整上下文。
  • 明確指定想要的產出格式與限制條件，減少來回修正。
  • 保存對話紀錄。它不只是備忘，也是之後量化效益、改善提問方式的資料。
